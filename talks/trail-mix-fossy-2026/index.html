trail mix: Open tempo, key, and waveform analysis

trail mix is an open source Rust toolkit for tempo, key, and waveform analysis of music files.

The talk explains why trail mix exists, how its analyzers work, and why the project is open source.

Cueport

Let's start with Cueport

Cueport is a local-first music player for people who own their music.

Let's start with Cueport

Cueport starts from the way DJs already work. Music files and DJ metadata live on the gig laptop, and tools such as Serato are used both for live playback and set preparation.

That metadata includes crates, cue points, tags, notes, labels, tempo, key, and waveform data. Cueport lets DJs cache selected music and metadata on a phone so they can review and edit away from the laptop, including in places with weak internet such as a flight or a venue.

Cueport is local-first

Cueport copies selected music and associated metadata from a laptop to a phone over a local connection. The usual path is LAN transfer on a private Wi-Fi network. On public Wi-Fi, where client isolation may block device-to-device traffic, the user can pair through a hotspot instead.

The QR code carries the connection details so the phone knows which desktop library to pair with.

Edits can be made on the phone while away from the laptop. When the devices pair again, mobile edits sync back to the desktop app for review.

Pairing is bidirectional: desktop data can move to the phone, and reviewed phone edits can move back to the desktop library.

Problem: DJ tool dependence

Cueport v1 depends on DJ tools for tempo, key, and beat analysis. That works for DJs who already use Serato, Rekordbox, or Traktor, but it does not help people who own and organize music outside those applications.

trail mix removes that dependency by generating the analysis directly from audio files.

trail mix

Solution: trail mix

trail mix accepts an audio file and returns tempo, key, beat positions, and waveform data as versioned JSON.

Solution: trail mix

An audio file first goes through the codec layer, which decodes (MP3, FLAC, WAV, AIFF, or MP4) into mono samples and a sample rate. The audio is now numbers: one amplitude value after another. Mono means the left and right channels have been combined into one signal, and the sample rate tells the analyzers how much time each sample represents.

trail mix uses deterministic signal-processing algorithms that compute from samples, not a trained neural model, cloud API, or separate analysis service.

Decode and normalization

Decoding turns an audio file such as MP3, FLAC, WAV, AIFF, or MP4 into evenly spaced amplitude values stored as sample buffers, usually one buffer for the left speaker and one buffer for the right speaker. The decoding layer then downmixes those buffers into one mono buffer. Downmixing combines the left and right samples at the same time position into one amplitude value, commonly by averaging them. After that step every format looks the same to the analyzers: samples and a sample rate. The core takes the buffer, not a file, so an app that already has playback samples can skip file decoding entirely.

Design

Why Rust for trail mix

trail mix is a Rust library because Cueport is a Rust app and the analysis has to run on-device with the same result every time.

Same language as Cueport
Cueport calls trail mix like any Rust crate, with no cross-language glue code to write or maintain.
No separate runtime
Compiles into Cueport's binary. Unlike Python or Java, no interpreter or garbage collector ships with it.
Memory-safe decoding
Unlike C or C++, a malformed audio file can't corrupt memory or open a security hole.
Native DSP performance
Compiles to native machine code, so the analyzers' heavy per-sample math runs fast.

Why Rust for trail mix

  • Same language as Cueport. Cueport is already written in Rust, so it can use trail mix directly, the same way it uses any other Rust crate. A C++ or Python implementation would need extra glue code to connect the languages.
  • Trail mix compiles right into the Cueport app, so there is no separate program to install and no background service. It just runs inside the app, with no internet. Languages like Python or Java would carry their own runtime along with the app, like a CPython interpreter or the JVM.
  • Safe with bad files. Opening someone's audio file means reading whatever is inside it, and a broken or hand-crafted file is a common way audio readers written in C or C++ crash or expose memory-safety bugs. Rust prevents many classes of memory corruption in the analysis code.
  • Fast enough on-device. The analyzers do a lot of math on every slice of the audio, and that has to feel instant on a laptop. Rust turns into fast machine code, so that heavy math keeps up.
  • The tradeoff. There was no existing Rust library for this kind of music analysis, so the analyzers were written in this project. The next accuracy step is to add small trained models rather than rewrite everything in another language.
Design

Why we built our own

The existing libraries in this space are solid, but no single one gave us a permissive, in-process API that also detects mid-track tempo and key changes and emits a versioned format.

Why we built our own

Skipping these was not about reinventing for its own sake. Each is strong at what it does, and we benchmark trail mix against several of them. The problem is that none could ship inside the product, and the reasons split cleanly into license, runtime, and scope.

  • stratum-dsp is the closest match: pure Rust, zero FFI, permissively licensed under MIT or Apache-2.0, and aimed at DJ apps. It reports one global BPM and key per track, while trail mix adds mid-track tempo and key changes, so the two projects overlap and could work together. Segmentation could be contributed upstream, or stratum-dsp could sit behind the same versioned Analysis JSON as an optional backend. It is benchmarked here as the closest permissive-Rust reference.
  • S-KEY is the most accurate key estimator on this list and is MIT licensed, so again not a license problem. It is a self-supervised model that needs a tensor runtime such as PyTorch or ONNX plus model weights, which is a heavier dependency than a small native Rust crate. It is used as a benchmark baseline, and the plan on the future-work slide is an ONNX version behind a feature gate.
  • libKeyFinder is the accurate key detector Mixxx uses, and it is used as a benchmark baseline, but it is GPL-3.0 C++, which cannot go inside a permissively licensed app. It is also the Queen Mary lineage: Mixxx's default beat and key detection comes from the Queen Mary plugins, so benchmarking libKeyFinder already covers that family.
  • Essentia is the broadest option, with tempo, key, beats, and much more, and it is used as a benchmark baseline. It is open source, so a Rust binding would be possible, but it is AGPL or a paid commercial license, so it cannot ship in the product either way.

The Benchmark baseline column means the tool is scored on the same corpora as trail mix. All four are: the standard key references S-KEY, libKeyFinder, and Essentia, plus stratum-dsp. stratum-dsp matters most as a baseline because it is the other permissive, pure-Rust DSP analyzer, so it is the closest architectural comparison. On FMAKv2 key it scores 0.48 MIREX (0.34 exact) against trail mix's 0.53, and on GiantSteps tempo it scores Accuracy1 0.60 and Accuracy2 0.85 against trail mix's 0.68 and 0.83. stratum-dsp also publishes its own numbers, 87.7 percent within 2 BPM and 72.1 percent exact key, but on a private 155-track DJ set with vendor-tag ground truth, so those are not comparable to the same-corpus figures here.

Waveform is left out of this comparison on purpose. It is the simplest of the three outputs, and the comparison here is about beats and key, which are the harder problems. The clear prior art for waveform overviews is BBC audiowaveform, but that is a concept we credit in the acknowledgements rather than code we copied, so it is not a dependency and does not belong on the open-source slide.

Mixxx is the main open-source DJ app rather than a reusable analysis library. It uses the Queen Mary plugins and, optionally, libKeyFinder, which is already in this table, so that lineage is represented. A Mixxx maintainer notes in a current pull request that they already store per-measure tempo and key but have not surfaced it to users.

The summary is that no single project combined a permissive license, an in-process Rust API, and mid-track key and tempo changes, which is why the analyzers are written from scratch. License was rarely the whole story: stratum-dsp and S-KEY are both permissive, and neither fit, one on scope and one on runtime.

Analyzer 1 of 3

Beat Salad

Tempo and beat positions

Beat Salad

Beat Salad is the tempo and beat estimation crate. It estimates one global tempo, a confidence score, regular beat positions, and windowed tempo segments from mono samples.

It is the most complex of the three analyzers in the current implementation. Multi-tempo tracks such as mashups and medleys are handled by the windowing covered later, in the beat-switch section.

Onset detection

An onset is where a new sound starts, like a drum hit. It shows up as a sudden jump in energy, so we track the energy frame by frame and add up only the rises. That running total is the onset-strength curve, and its peaks are the candidate beats.

Onset detection

An onset is where a new sound starts, like a drum hit or a plucked string, and it shows up as a sudden jump in energy. The audio is cut into short frames, and each frame measures how much energy increased since the frame before. Only increases count, because a sound getting louder is evidence for a new event while a sound fading out is not. Adding those increases gives one number per frame, the onset strength, and the sequence of those numbers is the onset-strength curve in the picture. Its peaks are candidate beats for tempo estimation and beat tracking. The implementation reads energy across 24 frequency bands spaced like musical pitch using Goertzel filters, and the summed rises are called spectral flux.

Tempo estimation and beat tracking

Tempo estimation finds the beat period that best matches the repeating peaks in the onset-strength curve. To find a beat switch, the same estimator runs on rolling sections of the track.

Tempo estimation and beat tracking

Global tempo is chosen by scoring candidate beat periods over the whole onset-strength curve. This does not require exact beat timestamps yet; it only needs evidence that onsets repeat at a regular interval. The intervals are measured between onset peaks, which are candidate musical events, not confirmed beats. The implementation combines two measures: an inter-onset interval histogram, which measures distances between onset peaks, and normalized autocorrelation, which measures how well the onset-strength curve aligns with itself at a lag. Candidates in the same half-time and double-time family are grouped so related tempos reinforce one reading, then a prior reduces common octave errors. The highest-scoring period sets global_bpm, and beat tracking uses that estimate on the next slide.

tempo_segments are separate from global_bpm. They are produced by running the same tempo estimator in rolling windows, 12 seconds wide with a 6-second hop, then grouping adjacent windows when the local BPM changes enough to matter.

Beat tracking with dynamic programming (DP)

Beat tracking uses the estimated BPM to place the actual beat timestamps. Tempo estimation gives BPM, but it does not choose the beat grid offset, that is where those beats start. DP helps choose which grid is most plausible across the whole track. It can keep the sequence regular when one beat is weak or missing, and it can skip a loud off-beat onset.

Beat Salad pipeline

This is the whole Beat Salad path in one picture. The samples become an onset-strength curve, tempo estimation picks the main beat period, and beat tracking turns that tempo estimate into timestamped beats by matching a regular beat sequence to the onset curve.

  • Onset detection uses frequency-band energy to build the onset-strength curve.
  • Tempo estimation works on that curve over time. The interval histogram counts how often different time gaps occur between onset peaks. For example, if 0.5 s gets a high score, it supports 120 BPM. Autocorrelation checks which time shifts make the onset curve line up with itself.

The output is a BeatAnalysis:

  • global_bpm is the dominant tempo for the whole file.
  • beats are the timestamped beat positions.
  • tempo_segments are detected by rerunning tempo estimation in rolling windows. They list time ranges with their own local BPM when the track has a meaningful tempo change.

Analyzer 2 of 3

Key Lime

Musical key from chroma

Key Lime

Key Lime estimates a major or minor key for the whole track, plus local key segments. The API always returns a tonic and a mode, for example A minor. Camelot, the DJ key notation used for harmonic mixing, is a display spelling only, which an app can add.

Key is the weakest analyzer in the current implementation, and the results slide quantifies the gap against the baselines.

Key detection from chroma

Take the 12-note chroma and compare it to a template for each key. The closest match, across all 24 major and minor keys, is the detected key.

\[\operatorname{score}(k) = \frac{\displaystyle\sum_{p=0}^{11}(c_p - \bar{c})\,(T_{p,k} - \bar{T}_k)}{\sqrt{\displaystyle\sum_{p=0}^{11}(c_p - \bar{c})^2 \;\cdot\; \sum_{p=0}^{11}(T_{p,k} - \bar{T}_k)^2}}\]

  • The formula: Pearson correlation; how closely the chroma matches a key template, after mean-centering and normalizing both
  • score(k): correlation for key k; the highest of 24 keys (12 major + 12 minor) wins
  • c_p: chroma energy at pitch class p (0-11, one per semitone)
  • T_{p,k}: expected energy for pitch class p in key template k (K-K, Temperley, EDMA, or an ML model)

Key detection from chroma

The 12-note chroma is the input to key scoring. Each of the 24 keys, 12 major and 12 minor, has a template with expected energy per pitch class. Key Lime measures how well the track's chroma matches each template with a Pearson correlation, then takes the best match. The implementation compares against several templates: Krumhansl-Kessler, Temperley, EDMA, and one built with ML from a corpus. It also includes refinements for tuning, relative-key disambiguation, and confidence-gated segmentation.

Key changes

Key Lime reruns chroma-to-template scoring in rolling windows, groups adjacent windows with the same confident key, and reports an alternate key when it covers at least 25% of the track.

Sampler Platter

Compact waveform overview

Sampler Platter

Sampler Platter bins mono samples into up to 1,500 columns, each summarized by minimum, maximum, and RMS, producing a Serato-compatible column layout for a waveform lane. The output is a WaveformOverview.

This analyzer is simpler than beat and key estimation: it summarizes the signal for display rather than inferring a musical label.

Sampler Platter

Waveform summarization

The min, max, and RMS columns that draw a track lane.

Waveform summarization

The implementation is local arithmetic over buckets. For each bucket, it computes min, max, and RMS, so the waveform overview does not need a separate DSP dependency.

Waveform implementation

The samples are split into up to 1,500 equally sized buckets. Each bucket becomes one column, summarized by three values.

let slice = &samples[start..end];
let min = slice.iter().copied().fold(f32::INFINITY, f32::min);
let max = slice.iter().copied().fold(f32::NEG_INFINITY, f32::max);
let sum_sq: f32 = slice.iter().map(|s| s * s).sum();
let rms = (sum_sq / slice.len() as f32).sqrt();
  • slice: the samples in this bucket (track length / up to 1,500 buckets)
  • min: lowest sample value; bottom edge of the waveform bar
  • max: highest sample value; top edge of the waveform bar
  • rms: root mean square energy; renderers can draw it as the filled region inside the bar

Waveform implementation

Each column maps one bucket of samples to min, max, and RMS. Those three values draw one vertical slice of the waveform lane.

Evaluation metrics

How to read the accuracy numbers on the next slide.

MIREX weighted score (key)
A wrong key is often musically close, so each track earns partial credit rather than pass or fail: an exact match scores 1.0, a perfect fifth 0.5, a relative major or minor 0.3, a parallel major or minor 0.2, and anything else 0. MIREX is the average of that credit over all tracks.
F1 at 70 ms (beats)
A predicted beat counts as correct when it lands within 70 ms of a real beat. From those matches, precision is the fraction of predicted beats that are correct and recall is the fraction of real beats found. F1 is the harmonic mean of the two, so it is high only when both are high: \(F_1 = \dfrac{2\,\times\,\text{precision}\,\times\,\text{recall}}{\text{precision}\,+\,\text{recall}}\), on a 0 to 1 scale.
Accuracy1 and Accuracy2 (tempo)
Accuracy1 counts a BPM as correct within four percent of the label. Accuracy2 also counts half-time or double-time as correct, because 70 and 140 BPM are the same pulse counted differently.
Hold out vs development
A development corpus is one we looked at while tuning. A hold out corpus is sealed before the run and never used for tuning, so it gives the fair score.

Evaluation metrics

This slide defines the metrics used on the results slide. The key metric is the MIREX weighted score. Each track is weighted by how musically related the guess is to the true key: exact 1.0, perfect fifth 0.5, relative major or minor 0.3, parallel 0.2, and 0 otherwise. The reported number is the average of those weights over all tracks, so near misses receive partial credit. The beat metric is F1 at a 70 millisecond tolerance. Precision is the fraction of predicted beats that land near a real beat, recall is the fraction of real beats found, and F1 is their harmonic mean. For tempo the standard pair is Accuracy1, correct within four percent, and Accuracy2, which also counts half and double time as correct. A development corpus was seen during tuning. A hold out corpus is sealed first, so it gives a fairer score.

Results and gaps

On FMAKv2, a 1000-track corpus sealed before anyone inspected results and never used for tuning, trail mix's DSP key detector scores 0.53 MIREX weighted (0.46 exact). The baselines ran on that same hold out set: S-KEY at 0.70, Essentia at 0.66 with its edma profile, libKeyFinder at 0.62, and stratum-dsp at 0.48 (0.34 exact). stratum-dsp is included because it is the other permissive, pure-Rust DSP key detector; on this corpus it scores 0.48 against trail mix's 0.53. Key is still the weakest analyzer overall, and the gap to the ML S-KEY model motivates the ONNX S-KEY backend on the next slide. GiantSteps was the development corpus used during tuning, where trail mix scores 0.49, so those runs are regression diagnostics rather than a hold out comparison. S-KEY is an ML model and FMAKv2 is Free Music Archive audio, so its training overlap is unknown and its 0.70 score may include some training-set exposure. The DSP tools, including trail mix, have no such training overlap.

For tempo, the slide reports global BPM on GiantSteps, which gives a same-run comparison across baselines. Trail mix scores Accuracy1 0.68 and Accuracy2 0.83. The DSP baselines are stratum-dsp at 0.60/0.85, Essentia at 0.61/0.80 with the degara method and 0.60/0.83 with multifeature, and librosa at 0.37/0.52. The ML Beat This model scores 0.86/0.94. stratum-dsp is close on the octave-tolerant Accuracy2 but lower on Accuracy1, meaning it lands a related pulse more often than the exact BPM label. GiantSteps is a development corpus inspected during tuning, so this is a diagnostic rather than a sealed comparison. On the hold out FSL10K tempo set, trail mix alone gets 0.43/0.59, lower because that set is short loops rather than full tracks.

The beat-placement metric, F1 at a 70 millisecond tolerance, is implemented in code, but scoring it needs a corpus that annotates every beat time. The corpora that cleared the provenance and license gate (GiantSteps, FSL10K, FMAKv2) label only global BPM and key. GTZAN-Rhythm was evaluated and rejected because its official audio is no longer distributed and its annotation repository has no explicit license, so an unofficial mirror would fail the gate. Other beat-tracking sets carry similar audio redistribution or licensing limits. Beat F1 therefore has no permissibly licensed ground truth wired in yet. Beat-tracking quality shows up indirectly through the tempo result and directly in the synthetic multi-tempo demo, where Beat Salad recovers both 120 and 90 BPM within about a tenth of a BPM. The stripped CLI binary with all common codecs is 1.7 MB, 2.0 MB unstripped.

Built with open source

trail mix builds on a number of Rust libraries. Symphonia handles decoding, turning an audio file into the samples the analyzers read. It is the heaviest dependency, but it lives in a separate decoding layer rather than on the core analysis path, so an app that already has samples can skip it.

For accuracy, trail mix is measured against open annotation sets with two roles. GiantSteps Tempo and GiantSteps Key are development corpora used during tuning; they are community EDM datasets with reference BPM and key labels annotated from user corrections, from Knees and colleagues at ISMIR 2015, with a follow-up crowdsourced tempo study by Schreiber and Müller in 2018. The hold out corpora used for external validation are FSL10K, the Freesound Loop Dataset, for tempo, and FMAKv2, key annotations over Free Music Archive audio, for key. Both annotation sets are distributed under CC BY 4.0 on Zenodo. The project imports labels and provenance while the audio keeps its own distribution terms, so the benchmark stores paths rather than redistributing recordings.

MIREX is not a dataset here. It is the scoring convention used for key: a weighted score that gives partial credit for musically close answers, so a perfect fifth or a relative major and minor pair earns something rather than zero. It sits on top of these datasets rather than being one of them.

The analyzers themselves are almost dependency-free. Beyond Serde there is no FFT or linear-algebra library, so the DSP is hand-written.

The analyze() function

One analyze() call runs the three analyzers over the same sample buffer and returns one versioned result.

pub fn analyze(audio: AudioBuffer<'_>) -> Analysis {
    let AudioBuffer { samples, sample_rate } = audio;
    Analysis {
        version: 1,
        beat: beat_salad::analyze(samples, sample_rate),
        key: key_lime::analyze(samples, sample_rate),
        waveform: sampler_platter::generate_overview(samples, sample_rate),
    }
}
  • AudioBuffer: the input, mono samples plus the sample rate
  • Analysis: the output, one versioned result with beat, key, and waveform
  • beat_salad::analyze: the analyze in the beat_salad crate, a different function from this one

The analyze() function

analyze is the one public entry point. It destructures the buffer into samples and a sample rate, then fills the beat, key, and waveform fields. Each analyzer lives in its own crate and exposes its own entry point, so beat_salad::analyze and key_lime::analyze are different functions that happen to share the name analyze, and the crate path in front makes each call unambiguous rather than recursive. The real signature also takes a config of per-analyzer settings and records a duration, which are dropped here to keep the shape clear. Same input, same output contract, three jobs.

Onset detection: spectral flux

The onset-strength curve is spectral flux, the summed rise in band energy from one frame to the next.

\[\operatorname{flux}(t) = \sum_{b=1}^{24} \max\!\bigl(0,\; E_b(t) - E_b(t-1)\bigr)\]

  • flux(t): onset strength at frame t; its peaks are the candidate beats
  • E_b(t): energy in band b at frame t, from 24 pitch-spaced Goertzel filters
  • max(0, ...): half-wave rectification, so only rising energy counts, not fading
  • sum over b: fold the rises across all 24 bands into one number per frame

Onset detection: spectral flux

This is the formula behind the onset slide. The audio is cut into short frames, and for each frame the energy is read across 24 frequency bands spaced like musical pitch using cheap Goertzel filters. For every band we take the rise since the previous frame and clamp negatives to zero, so a sound growing louder counts as a new event while a sound fading out does not. Summing those rises across the 24 bands gives one number per frame, the spectral flux, and the sequence of those numbers is the onset-strength curve whose peaks are the candidate beats.

Tempo estimation

Autocorrelation of the onset curve, together with an inter-onset interval histogram, locates the beat period. An octave prior then nudges the pick toward mid-range tempos to break the half and double time tie.

\[A(\tau) = \frac{\sum_t O(t)\,O(t-\tau)}{\sum_t O(t)^2}, \qquad \operatorname{prior}(\mathrm{bpm}) = \exp\!\left(-\frac{\log_2(\mathrm{bpm}/120)^2}{8}\right)\]

  • A(τ): normalized autocorrelation of the onset curve at lag τ; peaks mark repeating pulses
  • bpm(τ): tempo for lag τ, \(\mathrm{bpm}(\tau) = 60\,f/\tau\) with onset frame rate f
  • prior(bpm): soft preference near mid-range tempo, applied as \(0.75 + 0.25\,\operatorname{prior}\)
  • pick: the lag with the highest combined score sets the tempo

Tempo estimation

In the implementation the match strength for each candidate lag is a weighted blend, about 0.65 from an inter-onset interval histogram of the gaps between onset peaks and about 0.35 from the normalized autocorrelation shown here, which measures how strongly the onset curve repeats at lag tau. A lag converts to tempo by bpm equals 60 times the onset frame rate f divided by tau. Because half, true, and double time overlap, candidates in the same octave family are first grouped so related tempos reinforce one reading, then each is weighted by the octave prior, a Gaussian on log2 of bpm over 120 applied as 0.75 plus 0.25 times the prior, which favors mid-range tempos without hard-coding one answer. The best-scoring lag sets the tempo, and the interval histogram refines the final period. The autocorrelation term above is the periodicity piece of that combined score.

Beat tracking optimization

Ellis dynamic programming scores a whole beat sequence at once, rewarding strong onsets while keeping regular beat intervals.

\[C(i) = O(i) + \max_{j \lt i}\left[\,C(j) + w\,\exp\!\left(-\frac{\big((i-j)-P\big)^2}{2\sigma^2}\right)\right]\]

\[J(b_1,\ldots,b_m)=\sum_t O(b_t)+0.5\sum_{t>1}\exp\!\left(-\frac{\big((b_t-b_{t-1})-P\big)^2}{2\sigma^2}\right),\quad b_t-b_{t-1}\in[P-0.25P,\;P+0.25P]\]

  • C(i): best cumulative score for a beat ending at frame i
  • O(i): onset strength at frame i
  • P: target beat interval, \(P = 60\,f / \mathrm{BPM}\) with onset frame rate f

Beat tracking optimization

This is the optimization behind the illustration on the beat-tracking slide. C(i) is the best cumulative score for a beat ending at frame i, O(i) is that frame's onset strength, and P is the target beat interval, P equals 60 times the onset frame rate over BPM. The second line writes the same idea as a whole-path objective J over beat frames b. The interval reward is highest when a predecessor is about one period back, with sigma set to half a period and the reward weighted by 0.5. The implementation only searches predecessor gaps within about plus or minus 25 percent of P, which is the interval constraint shown at the end of the objective. Solving this for every frame in one forward pass gives the highest-scoring beat sequence for the whole track.

Beat tracking inner loop

The forward pass in Rust: for each frame, keep the best predecessor, then add the frame's own onset strength.

// beat interval in onset frames, and how far it may drift
let period = 60.0 * envelope_rate / bpm;
let denom = 2.0 * (period * 0.5).powi(2);
// for a beat at frame i, try each earlier frame j before it
let deviation = (i - j) as f32 - period;
let penalty = (-(deviation * deviation) / denom).exp();
let path = previous_score + penalty * 0.5;
// keep the best predecessor, then add i's own onset strength
let score = onset[i] + best_path;
  • period: ideal beat interval in onset frames, from the estimated BPM
  • penalty: Gaussian weight for a predecessor, highest when the gap i - j is one period
  • path: that predecessor's cumulative score plus the weighted interval reward
  • score: frame i's onset strength plus the best predecessor path

Beat tracking inner loop

This is the Rust forward pass for the optimization. period and denom are P and the Gaussian denominator. For a candidate beat at frame i the loop searches predecessor frames near one period back, scores each by that predecessor's cumulative score plus the interval reward weighted by 0.5, and keeps the best. Frame i's own onset strength is then added, and backtracing the best predecessors recovers the beat path.
