trail mix: DSP analysis with a compact transformer key reranker

trail mix is a Rust toolkit for local tempo, beat, key, and waveform analysis of music files.

This version also covers the compact key reranker, which raises global-key accuracy while keeping the same local Rust analysis API.

Cueport

Cueport

Cueport is a multi-device workstation for DJs that can import Serato libraries or construct local libraries directly from audio files.

Cueport

Cueport starts from the way DJs already work. Music files and DJ metadata live on the gig laptop, and tools such as Serato are used both for live playback and set preparation.

That metadata includes crates, cue points, tags, notes, labels, tempo, key, and waveform data. Cueport lets DJs cache selected music and metadata on a phone so they can review and edit away from the laptop, including in places with weak internet such as a flight or a venue.

Cueport Direct

Cueport Direct

Cueport Direct

Serato is still the first full integration, but Cueport Direct gives the app a path for people who do not have a Serato library. The user chooses one or more music folders. Cueport scans them into cueport-direct.db, stores collections, cues, notes, colors, restore points, and analysis there, and skips the Serato review and writeback flow because there is no external DJ library to publish into.

That is the product reason trail mix exists. If Cueport Direct imports folders directly from disk, it cannot import tempo, key, beat, and waveform analysis from Serato. It has to generate those values from the audio files themselves, locally and reproducibly.

trail mix

trail mix

trail mix is a Rust toolkit that decodes audio into mono samples and runs three analyzers behind one versioned JSON output.

trail mix

An audio file first goes through the codec layer, which decodes (MP3, FLAC, WAV, AIFF, or MP4) into mono samples and a sample rate. The audio is now numbers: one amplitude value after another. Mono means the left and right channels have been combined into one signal, and the sample rate tells the analyzers how much time each sample represents.

trail mix has three analyzers behind one compact local output contract. Give the names one beat here: beat salad, key lime, and sampler platter. The names are memorable, but they also map cleanly to the architecture. beat salad estimates tempo, beat positions, and local tempo sections. key lime estimates musical key from chroma, first with DSP template scoring and then with a compact reranker for the global key. sampler platter summarizes the waveform for display with min, max, and RMS columns.

key lime shows the main technical argument cleanly: pure DSP gives an interpretable local estimator, and a small transformer helps only where the DSP evidence is ambiguous.

Signal input and normalization

Decoding turns an audio file such as MP3, FLAC, WAV, AIFF, or MP4 into evenly spaced amplitude values stored as sample buffers, usually one buffer for the left speaker and one buffer for the right speaker. The decoding layer then downmixes those buffers into one mono buffer. Downmixing combines the left and right samples at the same time position into one amplitude value, commonly by averaging them. After that step every format looks the same to the analyzers: samples and a sample rate. The core takes the buffer, not a file, so an app that already has playback samples can skip file decoding entirely.

Why build a local analyzer?

Cueport Direct imports ordinary folders on a user's machine. That means analysis has to run in process, finish during library import, produce reproducible metadata, and avoid requiring a server.

The existing tools are useful references, not mistakes to avoid. stratum-dsp is the closest Rust DSP reference, but it reports global tempo and key rather than the local sections Cueport needs. S-KEY is a strong learned reference, but it needs a model runtime. A model runtime means shipping an inference engine such as PyTorch or ONNX Runtime plus the model weights. That adds binary size, platform-specific packaging, and another dependency to validate. For Cueport, the preferred boundary is a small native Rust analyzer that runs inside the app process. libKeyFinder and Essentia both matter as baselines, but their license terms do not fit a permissive in-app integration here. The reason for trail mix is the combination of license fit, local Rust API, mid-track changes, and versioned output.

Tempo estimator

beat salad

Tempo and beat positions

beat salad

beat salad is the tempo and beat estimation crate. It estimates one global tempo, a confidence score, regular beat positions, and windowed tempo segments from mono samples.

It is the most complex of the three analyzers in the current implementation. Multi-tempo tracks such as mashups and medleys are handled by the windowing covered later, in the beat-switch section.

Onset detection

Onset detection measures frame-to-frame increases in band energy and uses peaks in the resulting onset-strength curve as beat candidates.

Onset detection

An onset is where a new sound starts, like a drum hit or a plucked string, and it shows up as a sudden jump in energy. The audio is cut into short frames, and each frame measures how much energy increased since the frame before. Only increases count, because a sound getting louder is evidence for a new event while a sound fading out is not. Adding those increases gives one number per frame, the onset strength, and the sequence of those numbers is the onset-strength curve in the picture. Its peaks are candidate beats for tempo estimation and beat tracking. The implementation reads energy across 24 frequency bands spaced like musical pitch using Goertzel filters, and the summed positive changes are called spectral flux.

Onset detection formula

Spectral flux turns band-energy rises into one onset-strength value per frame.

\[\operatorname{flux}(t) = \sum_{b=1}^{24} \max\!\bigl(0,\; E_b(t) - E_b(t-1)\bigr)\]

  • E_b(t): energy in band b at frame t
  • max(0, change): count rises and ignore decays
  • sum over b: combine all 24 band changes into the onset-strength curve

Onset detection formula

This is the formula behind the onset slide. The audio is cut into short frames, and each frame reads energy across 24 frequency bands. For each band we keep only the positive rise since the previous frame. That means a sound growing louder counts as a new event, while a sound fading out does not. Summing across bands gives one onset-strength value per frame, and the peaks in that sequence become beat candidates.

Tempo estimation

Tempo estimation finds the repeated spacing between onset peaks and converts that spacing into BPM. Beat tracking is the next step.

Tempo estimation

Global tempo is chosen by scoring candidate beat periods over the whole onset-strength curve. This does not require exact beat timestamps yet; it only needs evidence that onsets repeat at a regular interval. The intervals are measured between onset peaks, which are candidate musical events, not confirmed beats. The implementation combines two measures: an inter-onset interval histogram, which measures distances between onset peaks, and normalized autocorrelation, which measures how well the onset-strength curve aligns with itself at a lag. Candidates in the same half-time and double-time family are grouped so related tempos reinforce one reading, then a prior reduces common half-time and double-time errors. The highest-scoring period sets global_bpm, and beat tracking uses that estimate on the next slide.

tempo_segments are separate from global_bpm. They are produced by running the same tempo estimator in rolling windows, 12 seconds wide with a 6-second hop, then grouping adjacent windows when the local BPM changes enough to matter.

Beat tracking with dynamic programming (DP)

Tempo gives the beat spacing. DP chooses the beat grid offset, skips loud off-beat peaks, and keeps the grid regular when a beat is weak.

Beat tracking with dynamic programming (DP)

Beat tracking uses the estimated BPM to place the actual beat timestamps. Tempo estimation gives BPM, but it does not choose the beat grid offset, that is where those beats start. DP helps choose which grid is most plausible across the whole track. It can keep the sequence regular when one beat is weak or missing, and it can skip a loud off-beat onset.

If the tempo is 120 BPM, the beat interval is about half a second, but many half-second grids could fit the same track. A greedy method can pick a loud off-beat peak and shift the rest of the grid. DP scores the full sequence at once: it rewards strong onset evidence, rewards intervals close to the tempo, and chooses the best global sequence rather than making one local decision at a time.

Ellis 2007 dynamic programming solves that as one sequence-scoring problem over the whole track. The next slide opens that objective so students can see where the regular beat grid comes from.

Beat tracking optimization

DP chooses the beat sequence with the best total score: strong onset peaks plus regular spacing near the estimated BPM.

\[ \hat{b}_{1:m}=\arg\max_{b_{1:m}} \left[ \sum_t O(b_t) + \lambda\sum_{t>1} R(b_t-b_{t-1}, P) \right] \]

  • b_t: candidate beat time t
  • O(b_t): onset strength at that beat time
  • P: target beat spacing from the estimated BPM
  • R(gap, P): spacing reward; highest when the gap is close to P
  • DP job: find the full beat sequence with the highest total score

Beat tracking optimization

This is the simplified objective behind the beat-tracking picture. The algorithm is choosing the whole beat sequence, not one beat at a time. The first term rewards beats that land on strong onset peaks. The second term rewards gaps between beats that are close to the period P implied by the estimated BPM.

The dynamic-programming implementation computes this efficiently by looking backward from each possible beat time to likely previous beat times. It gets a high reward when the gap is close to P, and a lower reward when the gap is early or late. The implementation searches only gaps within about plus or minus 25 percent of P. Solving this forward over the whole onset curve gives the best-scoring beat sequence.

Beat switches

beat salad reports a dominant BPM and an alternate tempo when a secondary tempo covers at least 25% of the track.

Beat switches

beat salad handles a beat switch by comparing local tempo estimates against the dominant global BPM.

  • global_bpm is the dominant tempo for the whole track.
  • multi_tempo is true when another tempo covers at least 25 percent of the track.
  • alternate_bpm reports that secondary tempo and its coverage fraction.
  • tempo_segments come from rolling-window tempo estimation and list the time ranges where each local BPM applies.

Beat-switch decision rule

Multi-tempo detection reruns tempo estimation in rolling windows and reports a secondary tempo only when it covers enough of the track.

\[ \begin{aligned} \widehat{b}_w &= \operatorname{tempo}(w) \\ b_r &= \operatorname*{mode}_{w \in r}\,\widehat{b}_w \\ q_r &= \frac{\operatorname{duration}(r)}{\operatorname{duration}(\mathrm{track})} \end{aligned} \]

  • w: a 12-second analysis window, advanced every 6 seconds
  • r: a contiguous run made by grouping neighboring windows whose local BPM estimates agree
  • b_r: representative BPM for that run of windows
  • Decision rule: report multi_tempo when \(|b_r - b_{\mathrm{global}}| > \delta\) and \(q_r \ge 0.25\)

Beat-switch decision rule

This formula describes the beat-switch detector rather than a new model. beat salad reruns tempo estimation in overlapping windows. Each window receives a local BPM estimate. The detector then walks along the track and groups neighboring windows into a run r when their local BPM estimates agree closely enough to represent the same local tempo. If the next window moves to a different local BPM, the current run ends and a new run starts.

The formula names the local tempo for each window, the representative tempo for a run of similar windows, and the fraction of the track covered by that run. A region becomes the alternate tempo only when it differs enough from the global BPM and covers at least a quarter of the track. That threshold prevents a short noisy section from turning into a multi-tempo result. In the demo, the 90 BPM half passes that coverage rule.

Waveform summarizer

sampler platter

Compact waveform overview

sampler platter

sampler platter bins mono samples into up to 1,500 columns, each summarized by minimum, maximum, and RMS, producing a Serato-compatible column layout for a waveform lane. The output is a WaveformOverview.

This analyzer is simpler than beat and key estimation: it summarizes the signal for display rather than inferring a musical label.

sampler platter

Waveform summarization

Column: one display column contains samples x_1...x_n.
Min: min = min(x_i), the lowest sample.
Max: max = max(x_i), the highest sample.
RMS: RMS = sqrt((x_1^2 + ... + x_n^2) / n), average energy.
Peak: peak = max(|min|, |max|), the largest absolute sample.
Drawn height: r = sqrt(peak * RMS); h is the final bar height after the app rescales r.
Band: b = 1...8 names the frequency band; E_b is energy in band b.
Band scale: p_b = (b - 1) / 7, so p_b runs from 0 for the lowest band to 1 for the highest.
Color: c = sum_b(p_b E_b) / sum_b(E_b), then hue = 10 + 200c.

Waveform summarization

Each display column keeps a small summary rather than the original audio. Start with one display column that contains samples x_1 through x_n. The stored shape values are min = min(x_i) and max = max(x_i). The stored energy value is RMS = sqrt((x_1^2 + ... + x_n^2) / n). The renderer derives peak = max(|min|, |max|), computes r = sqrt(peak times RMS), then rescales r across the segment. The result h is the final drawn height of that bar.

Color is separate. Inside that same display column, b = 1 through 8 names the frequency bands. The analyzer measures E_b, the energy in band b. The value p_b = (b - 1) / 7 is a normalized frequency coordinate: band 1 maps to 0, band 8 maps to 1, and the middle bands fall between those values. The spectral balance is c = sum_b p_b E_b / sum_b E_b. The renderer maps that balance to color with hue = 10 + 200c. The same E_b term is used in both sums, so c is an energy-weighted average of band frequency coordinates.

Key estimator

key lime

Musical key from chroma and a compact reranker

key lime

key lime estimates a major or minor key for the whole track, plus local key segments. The API always returns a tonic and a mode, for example A minor. Camelot, the DJ key notation used for harmonic mixing, is a display spelling only, which an app can add.

The global key is now chosen by a compact reranker that reads the same chroma sequence and DSP key scores that key lime already computes.

Vocabulary

Key vocabulary

These terms define the musical object that key lime predicts.

The note name without octave. One C key and the next C key up are an octave apart, and both are pitch class C.

A 12-value summary of how much audio energy belongs to each pitch class: C, C#, D, ... B.

The pitch class that feels like home or resolution in a specific song or section.

Key vocabulary

A pitch class is the note name without octave. One C key and the next C key up are an octave apart, and both are pitch class C. Chroma is a 12-value summary of how much audio energy belongs to each pitch class: C, C#, D, D#, E, F, F#, G, G#, A, A#, and B. Chroma is useful because key templates are also defined over those 12 pitch classes, so key lime can compare the track's chroma against the expected pitch-class pattern for each key.

The tonic is the pitch class that feels like home or resolution in a specific song or section. Mode is a scale type, such as major or minor. A key is a contextual label for a song or section, written as tonic plus mode, for example C major or A minor.

A key label combines a tonic and mode, for example C major or A minor. The global key is the one key label selected for the full track. The next slide explains how wrong labels are scored.

Key estimation as 24-way classification

Chroma measures energy in 12 pitch classes. The classifier predicts which pitch class is the tonic and whether the mode is major or minor.

Relative major/minor
A minor and C major share a key signature, so their chroma can be similar.
Parallel major/minor
A major and A minor share a tonic but differ in mode.
Perfect fifth
A and E are close in tonal function. Keys a fifth apart share many stable notes.
Unrelated key
Outside those relationships. Usually means the tonal center was missed entirely.

Key estimation as 24-way classification

This slide explains the classification problem. Chroma summarizes which note names are present in the audio, independent of octave. key lime uses that pitch-class pattern to choose one global key label. The label set is 12 tonic choices crossed with two modes, major and minor, giving 24 tonic-mode candidates. The later DSP pipeline shows how chroma is compared with templates to produce scores for those labels. The classifier still picks one label, but the wrong labels have different musical meanings.

MIREX weighted score gives partial credit when the predicted label is related to the reference key: 50 for a fifth, 30 for a relative major or minor, 20 for a parallel major or minor, and 0 for an unrelated key.

DSP key-estimation pipeline

Outputs by stage: windowed audio frames → pitch-class evidence → averaged 12-bin chroma → 24 key scores → global key with optional local segments.

DSP key-estimation pipeline

The DSP pipeline is the control system for the key estimator. Audio samples are decoded and downmixed once. The first output is windowed audio frames. The Goertzel and CQT branches turn those frames into pitch-class evidence. Averaging produces one 12-bin chroma representation. Profile matching turns that chroma into 24 key scores, one for each tonic-mode candidate. The final output is a global key, with optional local key segments from the DSP analysis.

That pipeline is useful by itself because it is small, deterministic, and inspectable. It is also useful as a learned-model input because the 24 DSP scores are already a compact musical prior. The reranker later uses that prior together with the chroma sequence.

Framing audio for key estimation

key lime analyzes short overlapping slices of audio. A Hann window fades each slice at the edges before frequency analysis.

  • Frame: a short slice of the audio signal
  • H: hop size between frames
  • Hann window: fades the frame edges so boundaries contribute less energy
  • Output: windowed audio frames for Goertzel and CQT pitch analysis

Framing audio for key estimation

The key estimator starts from the same mono PCM as the other analyzers. Instead of analyzing the whole track as one block, it cuts the signal into overlapping frames. A frame is a short slice of audio. H is the hop size, which is the step from the start of one frame to the start of the next frame. Because H is smaller than the frame length N, adjacent frames overlap.

Each frame is multiplied by a Hann window. The window is near zero at the frame edges and high in the middle, so the frequency analysis is driven by the center of the frame rather than by an abrupt cut at the boundary. In formula form, the windowed frame is \(x_m[n] = x[n + mH]w[n]\), where \(w[n] = 0.5 - 0.5\cos(2\pi n/(N-1))\). The output of this stage is a sequence of windowed audio frames. Those frames feed both pitch-evidence branches on the next slide.

Measuring pitch energy in each frame

Goal: turn each windowed audio frame into note-energy estimates. The next step folds those estimates into 12 chroma values.

  • Goertzel: ask a few chosen questions, such as "how much A is in this frame?"
  • CQT: build a broader note-spaced energy map across the pitch range
  • Output: note energy estimates for the next chroma-folding step

Measuring pitch energy in each frame

This slide explains the pitch-evidence stage in the pipeline diagram. At this point, key lime has a short Hann-windowed audio frame. The question is simple: which musical frequencies are strong in this frame?

Goertzel and CQT both measure pitch energy, but they answer different versions of the question. Goertzel is targeted. It asks a few chosen questions about the frame: how much energy is near A, how much is near C#, and how much is near their harmonics? CQT is broader. It builds a keyboard-shaped spectrum across many note-spaced bins, so the output lines up with musical pitch names rather than equal hertz steps.

Both branches produce note energy estimates per frame. The next slide shows the next operation: fold octave-related frequencies into 12 pitch classes to make chroma.

Output: 12-value chroma

This is the step where the pipeline first creates chroma: 12 values, one for each pitch class.

  • Input: pitch-frequency energy from Goertzel and CQT
  • Fold octaves: C2, C3, and C4 all add to the C pitch-class bin
  • Output: 12 chroma values, one for each pitch class
  • Next step: compare the chroma pattern with 24 key templates

Output: 12-value chroma

This slide connects the pitch-energy slide to the template-scoring slide. The input is pitch-frequency energy from Goertzel and CQT. The operation is octave folding: frequencies that are different octaves of the same note name add to the same pitch-class bin. For example, C2, C3, and C4 all support pitch class C. The output is a 12-value chroma vector, one value for each pitch class.

The important tradeoff is that chroma discards octave and voicing information. That is useful for key estimation because keys are defined by pitch classes, but it also means that related keys can look similar. The next slide compares the chroma pattern with 24 key templates, one for each tonic-mode label. The reranker later reads the frame-level chroma sequence to help resolve related-key confusions.

Key templates and scoring

A key template is a 12-value chroma pattern for one key. Compare the song chroma with 24 templates and pick the highest score.

  • c: the song chroma, 12 values for pitch-class energy
  • T_k: the key template for candidate key k, 12 expected chroma values
  • corr: Pearson correlation, high when the two 12-value shapes match
  • Selection: the highest of 24 template scores becomes the predicted key

Key templates and scoring

The 12-note chroma is the input to key scoring. Think of each key template as a 12-number fingerprint for what that key usually emphasizes. C major, for example, expects more support around pitch classes such as C, E, and G than around unrelated pitch classes. A minor has a different expected pattern.

key lime compares the song chroma \(c\) with every candidate template \(T_k\). There are 24 candidates because there are 12 possible tonic pitch classes and 2 modes, major and minor. The score is Pearson correlation after mean-centering and normalizing both vectors. In full form, \(\operatorname{score}(k)\) is the sum over pitch classes of \((c_p-\bar{c})(T_{p,k}-\bar{T}_k)\), divided by the product of their vector lengths. The highest of the 24 scores becomes the global key estimate.

Krumhansl-Kessler is one profile family. It comes from listener judgments about how stable each pitch class sounds inside a major or minor key, so it gives a 12-value expected pattern for a key. The shipped DSP scorer averages Krumhansl-Kessler, Temperley, EDMA, and a corpus-learned profile. The learned profile was generated by the trail mix profile-training script from GiantSteps Key benchmark output, which the repo marks as a development corpus and keeps separate from the sealed FMAKv2 holdout. That is not neural-model training, but it is supervised template calibration, so it belongs on the development side of the boundary. This matters because the reranker consumes these 24 DSP scores as input, so template provenance affects both KL-DSP and KL-FMAK. It also includes refinements for tuning, relative-key disambiguation, and confidence-gated segmentation.

Key evaluation metric

For each track, MIREX gives credit based on how close the predicted key is to the reference key, then averages those credits from 0 to 100.

Prediction relation Example if reference is C major Credit
Exact C major 100
Perfect fifth G major or F major 50
Relative major/minor A minor 30
Parallel major/minor C minor 20
Unrelated Any other key 0

\[s_i=\text{credit for track }i\text{ from the table},\qquad \text{MIREX}=\frac{s_1+s_2+\cdots+s_N}{N}\]

Key evaluation metric

Define the key metric before showing the results table. MIREX is a standard key-estimation scoring rule used in music information retrieval evaluations. For each track, compare the predicted key with the reference key. The score is not only correct or wrong. A musically related wrong key gets partial credit.

Using C major as the reference, C major receives 100. A fifth-related prediction such as G major or F major receives 50. The relative minor, A minor, receives 30. The parallel minor, C minor, receives 20. Any unrelated key receives zero. In the formula, s_i is the credit assigned to track i from this table. The dataset score is the average of those per-track credits, so it remains on a 0 to 100 scale. This deck uses MIREX as the primary key metric because it is the published comparison metric for FMAKv2 and because it distinguishes close key confusions from unrelated errors.

Why add a reranker?

trail mix is not only a key estimator. It also emits tempo, beat positions, local tempo sections, and waveform summaries. beat salad and sampler platter now have enough product coverage to discuss, while key estimation has the clearest measured reason for deeper modeling.

The pure DSP key scorer is compact and interpretable, but it scores 61.08 MIREX on the sealed 1,000-track FMAKv2 holdout. Local madmom scores 74.16 MIREX on the same files, a 13.08-point gap. key lime already has two inputs that can support a learned correction: frame-level chroma and the 24-dimensional DSP score vector. That motivates a compact reranker rather than a replacement model.

DSP-guided transformer reranker

Reranking means the DSP scorer proposes 24 key scores, then the learned model adjusts those scores using chroma-frame context.

  • 1. DSP ranks candidates: produce 24 scores, one for each tonic-mode label
  • 2. Chroma gives context: show how pitch-class energy changes across the first 256 frames
  • 3. Learned model adjusts scores: add a learned correction to the DSP ranking
  • 4. Highest adjusted score wins: choose the global key; local key segments remain DSP-based

DSP-guided transformer reranker

The reranker is deliberately small. key lime still extracts chroma, scores all 24 major and minor keys with DSP, and computes local key segments the same way as before. The learned part only reranks the global-key candidates.

Reranking means this: the DSP stage produces an initial score for each of the 24 key labels. The transformer reads the frame-level chroma sequence and learns a correction to those 24 scores. The corrected scores keep the same 24 tonic-plus-mode layout, and the highest corrected score becomes the selected global key. The local key segments remain DSP-based.

The selected model has 21,528 parameters. In the arXiv paper, the evaluated artifact is a 115 KB ONNX model, and the footprint table includes ONNX Runtime. In the Rust release, those same weights are embedded and the forward pass is written in Rust, so Cueport does not need ONNX Runtime, PyTorch, or a separate model service. Tests compare the Rust logits against ONNX reference fixtures with absolute error below 1.0e-4, so the packaged forward pass remains tied to the validated model.

Reranker architecture and parameter budget

The chroma branch makes 24 learned score corrections. The DSP branch carries the 24 DSP scores. Add them, then choose the largest score.

Reranker architecture and parameter budget

The architecture figure shows how the model uses two branches. The left branch reads frame-level chroma and turns the chroma sequence into 24 learned score corrections. The right branch carries the 24 DSP key scores through a learned 24-by-24 projection. That projection starts as the identity, meaning it initially copies the DSP ranking rather than changing it.

The outputs are summed as logits over the same 24 key classes. Logits are unnormalized key scores. This is the concrete implementation of the residual reranking idea: start with the DSP ranking, add learned corrections from chroma context, then select the largest adjusted score. The parameter budget is deliberately small. The whole model has 21,528 trainable parameters.

How the reranker is trained

Training teaches the reranker when chroma context should change the DSP ranking.

Step What happens
1. Read inputs first 256 chroma frames (about 32 s) plus 24 DSP scores
2. Learn the answer predict the FMAKv2 key label; related keys get small partial credit
3. Update weights AdamW updates model weights; validation decides when to stop
4. Test variants transpose examples, try easy-to-hard ordering, and test teacher distillation

How the reranker is trained

This slide tells the training story rather than listing every hyperparameter. The reranker reads two inputs: the first 256 chroma frames, which covers about 32 seconds, and the 24 DSP key scores. It learns to predict the FMAKv2 key label from those inputs.

The target is MIREX-aware rather than one-hot only. The true key receives most of the mass, while a small amount is spread over musically related fifth, relative, and parallel neighbours. AdamW updates the model weights with learning rate 0.001, batch size 16, at most 25 epochs, class balancing, dropout 0.3, weight decay 0.05, and validation-based early stopping.

The tested variants are there to check which training choices matter. Transposition augmentation rotates each input sequence and label through all 12 semitones. The DSP-margin curriculum starts with tracks where the top DSP score is clearly separated from the runner-up, then adds harder tracks over five epochs. Ordering can affect a neural model because training updates weights step by step. Early examples shape the solution that later examples refine.

Teacher distillation means that another model supplies a soft target, not just a single hard label. For each track, the frozen madmom KeyCNN teacher produces probabilities over the same 24 key labels. The optional distilled reranker is trained partly to match the FMAKv2 label and partly to match those teacher probabilities. The α = 0.3 setting gives the teacher term 30 percent of the target weight, and temperature T = 4 smooths the teacher probabilities so near-miss labels carry more information. The final reported model is the label-trained version, because the distilled comparison did not improve MIREX.

Which input features help?

This comparison is important because it explains why the reranker works. In machine-learning terms this is an ablation study: remove or replace one feature group and see how the metric changes. The only-24-DSP-key-scores row is still a reranker, but it only learns how to reweight the 24 DSP scores. It does not read the chroma-frame sequence. It scores 60.25 MIREX, below the 61.08 KL-DSP baseline, so reranking the DSP scores by themselves is not enough. The improvement appears when the reranker also reads frame-level chroma, which gives it time-local pitch evidence beyond the final DSP ranking.

The final DSP scores plus chroma frames model scores 73.55 MIREX, while the teacher-distilled variant scores 72.50. The paper reports label-trained minus teacher-distilled as +1.05 MIREX with a 95 percent confidence interval of -0.43 to +2.51, so teacher distillation is optional rather than required for the reported gain. The DSP-margin curriculum is an easy-to-hard training order based on how separated the top DSP key scores are. Removing it gives 73.16 plus or minus 0.62 MIREX, close to the final model.

The circular input stage uses 12 trainable weights, compared with 468 for a plain linear projection over chroma inputs. The linear-projection comparison remains in the same accuracy range, so the circular stage is kept because it encodes pitch-class rotation structure at much lower input-stage parameter cost.
